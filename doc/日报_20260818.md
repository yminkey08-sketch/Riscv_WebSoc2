# 日报 2026-08-18

## 重新学习固件 — 第4天：icmp 层

> 按计划吃透 icmp 层：ping 的本质就是 ICMP echo 请求/回复，今天理解 `icmp.c` 怎么回显、ICMP 校验和怎么算。

### 学到了什么

**icmp 层（`c/icmp.c`，109 行）**：ICMP 是网络诊断协议，固件里只处理最常用的一种——**echo request → echo reply**，也就是 ping。核心是 `icmp_reply()`：收到 ping 请求，把 type 从「请求」改成「回复」、原样回显数据，重算校验和发回去。

**`icmp_reply()` 流程（`icmp.c:58-109`）**：

1. 先 `ip_header_update(src_ip, ip_total_len)` —— 改 IP 头（第3天学的），icmp 层只负责 ICMP 段
2. 改 type：`8(request) → 0(reply)`，code 保持 0
3. 拷贝 identifier + sequence（字节 4-7，回显让客户端能匹配请求）
4. 拷贝 payload（字节 8 之后，原样回显）
5. 算 ICMP 校验和（type 变了必须重算）
6. 补 0 到 64 字节最小帧，push

**ICMP 校验和（`icmp_body_checksum`，`icmp.c:14-56`）**，和 IP 校验和的三个区别：

| 区别 | IP 校验和（第3天） | ICMP 校验和（今天） |
|------|------------------|-------------------|
| 覆盖范围 | 只算 20 字节头 | 整个 ICMP 消息（头8 + 数据） |
| 伪首部 | 无 | 无（TCP 才有） |
| 起始词 | 从头算 | 从 type+code=0x0000 开始 |

关键点：
- 起始 `cks_sum_cal(0x00, 0x00, 0)` = type+code 这个词（reply 的 type=0、code=0）
- checksum 字段本身（字节 2-3）跳过不算——因为计算时它就是 0，加不加都一样
- identifier/sequence/payload 从 RX 读回参与累加
- **奇数长度要补 0**：payload 是奇数个字节时，最后一个字节单独配 0 高位（`icmp.c:50-54`）

**回显的原理**：ping 客户端发 request 时带上 identifier（区分进程）、sequence（区分序号）和一段数据，服务端 reply 时**原样返回**这三样，客户端据此匹配「这个 reply 对应我哪个 request」。所以 `icmp_reply` 里 id/seq/payload 全是「从 RX 读回写回」，一个字节都不改。

### 关键精髓

- **type 8→0 是 icmp_reply 的「一句话核心」**：改一个字节，request 就变 reply。
- **校验和覆盖范围因协议而异**：IP 算头、ICMP 算整包、TCP 算伪首部+头+数据，别记混。但底层都是同一个 `cks_sum_cal()` 反码折叠。
- **回显三件套**：identifier + sequence + payload 原样返回，是 ping 能工作的机制基础。
- **分层接力**：icmp 层不碰 MAC 头（eth 写的）、不碰 IP 头（ip_header_update 改的），只写 ICMP 段——延续前几天的「分工流水线」。
