# RiscV WebSoC2 项目开发记录

## 项目背景

在 XC7A35T FPGA（ALINX ACX750 开发板）+ RTL8211F 千兆 PHY 上，基于 PicoRV32 RISC-V 软核实现 TCP/IP 协议栈和 Web 服务器。PC 通过网线直连 FPGA，能 ping 通、浏览器能打开网页。

---

## 第一阶段：Ping 调通（8月3-4日）

### 初始状态
- 作者 v3 预编译固件（RiscV_WebSoC(3).7z）能 ping 通、HTTP 可访问
- 自写 v2 固件（RiscV_WebSoC2.7z）ping 不通，ARP 无应答

### 问题定位

**1. FIFO 访问方式错误（关键根因）**
- 自写代码采用内存缓冲方式：`eth_rx_frame()` 将整帧读到 `rx_buffer[1518]`，处理后再 `eth_tx_frame()` 逐字节写回 TX FIFO
- 作者 v3 代码采用原地 FIFO 直接读写：`LCPU_RD_DATA8()` 从 RX FIFO 读，`LCPU_WR_BYTE()` 直接写 TX FIFO，无中间缓冲区
- 解决：将源码替换为 v3 风格的原地 FIFO 处理

**2. base bitstream 不匹配**
- updatemem 嵌入固件后 CPU 不执行——原因是用的 `impl_1/webserver_cpu_top.bit` 和 MMI 文件层次不匹配
- 解决：从 v3 项目提取 `RiscV_WebSoC_v3base.bit` 作为 updatemem 输入

**3. GCC 版本差异 — linker.ld**
- GCC 12.2.0 生成 `.note.gnu.build-id` 段占据地址 0x00-0x23，把 `reset_entry` 挤到 0x24
- CPU 上电从地址 0 取指，读到 build-id 的垃圾数据立即崩溃
- 解决：linker.ld 加 `/DISCARD/ : { *(.note*) *(.comment*) }`

**4. updatemem 工作目录问题**
- `make` 在 `c_build/` 执行，`updatemem` 必须在 `build_xilinx/` 执行（该目录有 MMI 和 base bitstream）
- 反复犯同一错误：updatemem 从错误目录运行，显示帮助信息

**5. 烧录后需等待 PHY 建链**
- FPGA 重新配置后 PHY 需要约 5 秒重新建立链路
- 刚烧录完立即 ping 会 "Destination Host Unreachable"

## 第二阶段：TCP 协议栈实现（8月4-5日）

### 开发计划（7 步）

| 步骤 | 内容 | 状态 |
|------|------|------|
| 1 | 发送发动机（fill_tcp_header + checksum + send_tcp_seg） | ✅ |
| 2 | 接收解析器（从 RX FIFO 读 TCP 头） | ✅ |
| 3 | 连接表管理（并行数组） | ✅ |
| 4 | 三次握手（SYN → SYN+ACK → ACK） | ✅ |
| 5 | 数据收发（PSH+ACK + payload） | ✅ |
| 6 | 连接断开（FIN + TIME_WAIT） | ✅ |
| 7 | HTTP 网页 | ✅ |

### 代码结构

- `c/inc/lcpu_general.h`：v3 风格寄存器宏（`_RD(n)`/`_WR(n)` 直接 volatile 指针）
- `c/eth.c`：`eth_proc()`，检测以太类型 + 校验目的 MAC + 写 MAC 头到 TX FIFO
- `c/arp.c`：`arp_reply()`，原地构建 ARP 应答，内部调 `LCPU_WR_PUSH_PACKET`
- `c/ip.c`：`ip_proc()` + `ip_header_update()` + `ip_header_checksum()`
- `c/icmp.c`：`icmp_reply()`，原地构建 Echo Reply
- `c/tcp.c`：完整 TCP 协议栈（状态机、定时器、校验和）
- `c/inc/tcp.h`：连接表定义、状态常量、Flag 定义
- `c/main.c`：`program_main()` 主循环

### TCP 实现要点

**连接表**：并行数组而非结构体，避免 RISC-V 对齐问题
```c
uint8_t  connection_states[MAX_CONNECTIONS];
uint32_t connection_seq_nums[MAX_CONNECTIONS];
uint16_t connection_src_ports[MAX_CONNECTIONS];
// ... 等 12 个数组
```

**状态机**：CLOSED → SYN_RECEIVED → ESTABLISHED → FIN_WAIT → TIME_WAIT → LAST_ACK

**定时器**：`tcp_periodic_check()` 处理 TIME_WAIT 超时、空闲超时 RST、SYN+ACK 重传

### TCP 调试踩坑

**1. 端口交换 bug（导致三次握手失败）**
```c
// 错误：fill_tcp_header 中源端口和目的端口没交换
hdr[0] = (sp >> 8) & 0xFF;  // sp = connection_src_ports（PC端口）
hdr[2] = (dp >> 8) & 0xFF;  // dp = connection_dst_ports（80）
// SYN+ACK 响应中源端口应该是 80（FPGA），目的端口是 PC 端口——写反了

// 修复：交换
hdr[0] = (dp >> 8) & 0xFF;  // SRC = FPGA port (80)
hdr[2] = (sp >> 8) & 0xFF;  // DST = PC port
```
修复后 `nc -vz 169.254.1.1 80` 通过。

**2. LCPU_SET_LED 在 FIFO 操作期间调用会破坏网络通信**
- 在 `eth_proc`/`ip_proc` 内部调用 `LCPU_SET_LED` 做调试断点，导致 ping 不通
- Led 写总线操作与 RX/TX FIFO 操作在同一总线上，可能引起冲突
- 解决：LED 调试代码放在 `_RD(1)=1`（RX POP）之后

**3. TCP 连接不释放**
- 忘了在主循环调用 `tcp_periodic_check()`，导致 LAST_ACK 连接永远不回收
- 加 `tcp_periodic_check()` 到 while(1) 循环中

**4. curl 代理问题**
- `curl http://169.254.1.1/` 返回 502 Bad Gateway——走了 127.0.0.1:7897 代理
- 解决：`curl --noproxy '*' http://169.254.1.1/`

**5. HTTP 响应超时（ip_header_update 硬编码失败）**
- 尝试把 `ip_header_update` 中从 RX FIFO 读 IP 头改为硬编码值
- 结果 ICMP 协议号被写死为 TCP(0x06)，ping 也挂了
- 回退到原始 RX FIFO 读取方式

## 第三阶段：LED 控制和 HTTP 网页（8月5-8日）

### TCP 短连接 LED 控制
- TCP payload 第一个字节作为 LED 值
- Python 客户端：`led_client.py`，发单字节控制 4 路 LED
- MAX_CONNECTIONS=8，`tcp_periodic_check()` 清理连接

### HTTP 网页服务器
- `send_http_response()`：构建 HTTP/1.1 200 + HTML 页面
- HTML 页面含 6 个 LED 控制按钮，CSS 深色主题
- URL 解析：`GET / HTTP/1.1` 返回主页，`GET /led/0F HTTP/1.1` 设置 LED=0x0F 后返回主页
- 去掉 main.c 中心跳流水灯，避免覆盖 HTTP 设置的 LED

## 第四阶段：仿真环境搭建（8月5-8日）

### iverilog 仿真

**环境组成**：
- `sim/tb.v`：testbench，GMII 包注入 + TX 监控
- `sim/vendor_stubs.v`：BUFG/IDDR/ODDR/IDELAYE2/MMCME2 等 Xilinx 硬核行为模型
- `sim/xpm_memory_tdpram_sim.v`：XPM 真双口 RAM 行为模型
- `sim/lcpu_bfm.sv`：通过 TCL 脚本加载固件的 BFM

**GMII 旁路**：修改 `webserver_cpu_top.v`，sim_mod=1 时暴露 GMII 直连接口，跳过 RGMII 桥的 DDR 时序复杂性

**调试经历**：
- RTL 内置自检测试（gmii2mac、package_fifo、uart 等模块含 `initial begin` 测试块）拖慢仿真速度，每次 60 秒+
- `jwrite 0x100 0x0` 在 BFM 路径下只是程序 RAM 写（不是 reset 控制），会破坏地址 256 的指令；小固件（17 字）不受影响
- BFM 加载 1300 字需 ~270µs，testbench 初始等待需 ≥500000 才能正确初始化
- 完整固件仿真中无 TX 响应——怀疑 125MHz GMII 时钟精度

**结果**：仿真可加载极简固件（LED 从 0x0F→0x00），速度太慢不实用

### Verilator 仿真

**环境组成**：
- `sim_verilator/vtop.v`：Verilator 顶层封装，sim_mod=1
- `sim_verilator/sim_main.cpp`：C++ testbench，GMII 包注入、LED 监控
- `sim_verilator/Makefile`：`--public-flat-rw --timing --top-module vtop`

**问题与解决**：
- Verilator 比 iverilog 严格，编译提示大量端口和参数缺失
- 逐一补齐 `altsyncram` 和 `xpm_memory_tdpram` stub 的缺失端口（`clocken2/3`、`byteena_a/b`、`rden_a/b`、`eccstatus`、`power_up_uninitialized`）
- 固件改为 `$readmemh` 预加载到 BRAM，绕过 BFM
- 需添加 `$readmemh` 条件判断——否则所有 XPM 实例（含 FIFO）都加载固件
- 16 个指令 bank 各自从 firmware.hex 起始加载（非分段），完整固件在跨 bank 地址处崩溃
- 极简固件（17 字）仿真通过：LED=0000，~10 秒完成（iverilog 需 60 秒+）

## 关键经验总结

1. **原地 FIFO 处理**是正确的工作方式——不能把数据拷到内存缓冲区再写回
2. **updatemem** 必须从 `build_xilinx/` 运行，base bitstream 需与 MMI 匹配
3. **GCC 12.2.0** 需要 linker.ld 中 `/DISCARD/` 丢弃 .note 段
4. **TCP 端口交换**：响应包中 src/dst port 和 src/dst IP 都要交换
5. **LED 调试**：不能放在 FIFO 操作期间，应放在 `_RD(1)=1` 之后
6. **tcp_periodic_check**：必须在主循环调用，否则连接永不释放
7. **Verilator** 速度快但端口匹配严格，需完整 stub 模型
8. **$readmemh 预加载**：需按 bank 拆分固件，否则跨 bank 地址错乱
