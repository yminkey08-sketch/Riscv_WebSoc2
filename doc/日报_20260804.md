## 任务一：Ping 固件问题定位与修复

### 进展和结果
- 成功定位 ping 不通的根因：**FIFO 访问方式错误 + base bitstream 不匹配**
- 修复后重新编译烧录，**Ping 169.254.1.1 通过**，ARP 请求/应答、ICMP 请求/应答均正常
- LED 流水灯正常运行

### 遇到的问题

1. **Ping 不通（关键踩坑）**：
   - 原始代码采用**内存缓冲区方式**：`eth_rx_frame()` 将整帧读到 `rx_buffer[1518]`，处理后 `eth_tx_frame()` 逐字节写回 TX FIFO
   - 作者已验证的 v3 代码采用**原地 FIFO 直接读写**：`LCPU_RD_SET_ADDR()`/`LCPU_RD_DATA8()` 从 RX FIFO 直接读，`LCPU_WR_BYTE()` 直接写 TX FIFO，**没有中间缓冲区**
   - 另外发现 v3 代码的 `arp_reply()` 和 `icmp_reply()` 内部自带 `LCPU_WR_PUSH_PACKET()`，调用方不再额外 PUSH

2. **updatemem 后固件不运行**：
   - 初始使用 `impl_1/webserver_cpu_top.bit` 作为 base bitstream，updatemem 成功但 CPU 不执行代码（LED 无反应）
   - 换成 v3 项目的 `RiscV_WebSoC_v3base.bit` 后正常

3. **GCC 版本差异**：
   - Xilinx Vitis GCC 12.2.0 生成 `.note.gnu.build-id` 段，占据 0x00-0x23，把 `reset_entry` 挤到 0x24 → CPU 上电取指拿到垃圾
   - xPack GCC 14.2.0 无此问题（`reset_entry` 在 0x00）
   - 修复：`linker.ld` 加 `/DISCARD/ : { *(.note*) *(.comment*) }`

### 解决方法/经验总结

1. **FIFO 访问规则**：
   - 直接从 RX/TX FIFO 逐字节读写，不能拷贝到内存缓冲区
   - `eth_proc()` 在处理收包时同时写 MAC 头到 TX FIFO（原地 swap）
   - `ip_proc()` 读 IP 头验证，`ip_header_update()` 写 swap 后的 IP 头到 TX FIFO
   - `arp_reply()`/`icmp_reply()` 内部调 `LCPU_WR_PUSH_PACKET()`

2. **Base bitstream 选择**：
   - 必须使用与 MMI 文件匹配的 base bitstream
   - 从已验证的 v3 项目提取 `RiscV_WebSoC.bit` 作为 updatemem 输入

3. **固件架构对比**：
   | | v2 原版（不通） | v3 作者版（能通） |
   |---|---|---|
   | 包处理方式 | 内存缓冲 (`rx_buffer[1518]`) | 原地 FIFO 直接读写 |
   | `arp_reply` PUSH | 外部调用 | 内部自带 |
   | MAC 地址 | 02:00:00:12:34:56 | 00:00:01:02:04:05 |
   | 代码量 | ~2.2KB | ~2.4KB |

## 任务二：TCP 协议栈学习与计划制定

### 进展和结果
- 完整学习 TCP 协议基础：
  - **报文格式**：固定头 20 字节（SrcPort + DstPort + SEQ + ACK_Num + DataOffset + Flags + Window + Checksum + Urgent）
  - **六个 Flag**：FIN(0x01) / SYN(0x02) / RST(0x04) / PSH(0x08) / ACK(0x10) / URG(0x20)
  - **三次握手**：PC SYN(SEQ=x) → FPGA SYN+ACK(SEQ=y, ACK=x+1) → PC ACK(SEQ=x+1, ACK=y+1)
  - **TCP 校验和**：需 12 字节伪首部（SrcIP + DstIP + Zero + Proto + TCP_Length），覆盖伪首部 + TCP头 + Payload
  - **状态机**：CLOSED → LISTEN → SYN_RECEIVED → ESTABLISHED
  - **关键规则**：SYN 和 FIN 各占一个序号，ACK_Num = 对方SEQ + 1

### TCP 开发 7 步计划

| 步骤 | 内容 | 可独立验证 |
|------|------|-----------|
| 1 | 发送发动机（`fill_tcp_header` + `tcp_checksum_build` + `send_tcp_segment`） | 否，需绑接收 |
| 2 | 接收解析器（从 RX FIFO 读 TCP 头，提取 src_port/dst_port/seq/ack/flags） | 否，需绑连接表 |
| 3 | 连接表管理（并行数组：dst_ip/dst_port/src_port/seq/ack/state） | 否 |
| 4 | 三次握手（`tcp_packet_handler` → SYN → `send_syn_ack` → ACK → ESTABLISHED） | 是，`nc -vz` 验证 |
| 5 | 数据收发（PSH+ACK 处理 + payload 拷贝） | 是，echo server |
| 6 | 连接断开（FIN 处理 + TIMED_WAIT） | 是 |
| 7 | HTTP 网页（端口 80 GET 请求 → 返回 HTML） | 是，浏览器验证 |

### 遇到的问题
- 参考两篇日报中的经验，**TCP 发送不能脱离收包流程独立运行**：MAC 头由 `eth_proc()` 写入，IP 头由 `ip_header_update()` 写入，TCP 层只写 TCP 段
- 步骤 1 的发送原语代码逻辑独立可写，但验证需要步骤 2+3 打通后才能进行

### 解决方法/经验总结
- 步骤 1-3 并行开发，步骤 4 串联验证
- 连接表用并行数组（`connection_dst_ips[]` / `connection_states[]` 等），避免结构体偏移在 RISC-V 上的对齐问题
- 校验和计算复用现有 `cks_sum_cal()`，TCP 校验和覆盖伪首部 → TCP 头 → 载荷
