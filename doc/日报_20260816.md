# 日报 2026-08-16

## 重新学习固件 — 第2天：arp 层

> 按计划吃透 arp 层：ARP 是「IP 地址 → MAC 地址」的查询协议，今天理解 `arp.c` 怎么校验请求、怎么构造 reply。

### 学到了什么

**arp 层（`c/arp.c`，106 行）**：PC 想跟 FPGA 通信但只知道它的 IP、不知道 MAC 时，就广播一个 ARP request 问「谁的 IP 是 169.254.1.1？」，FPGA 收到后单播回一个 reply 报上自己的 MAC。整个文件就一个函数 `arp_reply()`，干的是「校验是不是问我的 → 是就回 reply」。

**三层校验（`arp.c:22-41`），全过才回**：

1. 目的 MAC == 本机 MAC，或 == 广播 `ff:ff:ff:ff:ff:ff`
2. target IP == 本机 IP（`0xA9FE0101` = 169.254.1.1）
3. opcode == request（`0x0001`）

**构造 reply 的「拷 + 改」思路**：不重新拼一个 ARP 帧，而是把 request 的字段按位置拷过来、只改几个关键位置：

- **只改 4 处**：opcode `1→2`、src MAC = 本机、sender MAC/IP = 本机、target MAC/IP = 对方的 sender
- **其余照抄**：htype/ptype/hlen/plen（14-19 字节）这些协议元数据原样拷贝（`arp.c:66-69`）
- **dst MAC 是单播不是广播**：request 的 sender_mac 里就带着请求方 MAC，reply 直接单播回给它（`arp.c:45-49` 把 RX[6..11] 的 src MAC 拷成 TX[0..5] 的 dst MAC）

**为什么 arp.c 要自己搭整个以太网帧**：回看第 1 天的 eth.c——`eth_proc()` 只对 IP 包做了「预写 MAC 头」，ARP 分支是直接 `return ARP_PROC` 什么都没写（`eth.c:16-18`）。所以 arp.c 得从字节 0 开始，把以太网头（14 字节）+ ARP 负载（28 字节）全部自己写。

**补到 64 字节**：以太网最小帧 64 字节，ARP 帧只有 42 字节，后面补 0（`arp.c:101-103`）。

### 关键精髓

- **ARP 是「一问一答」**：request 广播、reply 单播。reply 的目的 MAC 就藏在 request 的 sender_mac 里，不用再广播一遍。
- **校验要严格**：收到广播 ARP（可能是问别人）也要检查 target IP 是不是自己，不是就静默丢弃——广播包人人都会收到，但只有被问的那个该回。
- **「拷 + 改」比「重建」高效**：协议头大部分字段是固定值（htype=1、ptype=0x0800、hlen=6、plen=4），照抄就行，只有 opcode 和 sender/target 要动。省内存、少出错。
