# 日报 2026-08-11

## Verilator 仿真环境修复

### 进展和结果
- 定位 Verilator 仿真无法运行全功能固件的根因：缺失 `xpm_memory_sdpram` 仿真模型
- 创建 `xpm_memory_sdpram_sim.v`：Simple Dual-Port RAM 行为模型，覆盖 common_clock 和 independent_clock 两种模式
- 修复 sdpram 模型 `addressstall` 浮空导致读写被阻塞的 bug（RTL 中该端口未连接）
- 重写 `xpm_memory_tdpram_sim.v`：使用 `%m` 实例路径自动解析 bank 编号，支持 per-bank 固件加载
- 实现双模式固件加载：优先 `firmware.hex`（极简测试），回退 `firmware_bankN.hex`（完整固件）
- 从 `firmware.bin` 生成 16 个 per-bank hex 文件（每 bank 256 words），仿真启动时自动加载
- 修复测试包缺少 Ethernet preamble 的问题：`send_gmii()` 添加 7×0x55 + 0xD5 SFD

### 遇到的问题
1. **Verilator `%m` 字节反转**：`$sformat(_ipath_, "%m")` 在 Verilator 中将实例路径逐字符反转存储，需在解析 bank 编号时同时处理正序和逆序括号
2. **reg 宽度陷阱**：`reg [127:0]` 是 128bit = 16 字节，不是 128 字节。文件名 "firmware_bank0.hex"（19 字符）被截断为 "firmware_bank0.h"，导致 `$fopen` 失败。改为 `reg [255:0]`（32 字节）
3. **`// Verilator` 注释被当作 pragma**：Verilator 将 `// Verilator xxx` 格式注释也解析为 pragma 指令，报 "Unknown verilator comment" 错误。需避免在注释行首使用该词
4. **`$fgets`/`$sscanf` 字符串宽度限制**：Verilator 对 `$sscanf` 的字符串参数有 `VL_VALUE_STRING_MAX_WORDS` 硬限制，8192-bit 的 reg 超出限制。改为 `$fgetc` + 逐字符解析
5. **BFM 与 lcpu_merge 时序竞争**：initial 块中阻塞赋值与 always 块的 @(posedge clk) 存在 Verilog 事件队列竞争。改为 NBA 配合额外等待周期，或直接使用 XPM 模型预加载绕过 BFM
6. **eth_presemble 模块 preamble 检测**：`rx_presemble_en=1` 时，MAC 层仅在检测到 0x55...0xD5 序列后才透传数据。测试包必须包含完整 preamble

### 当前状态
- ✅ 极简固件通过（LED=0000），确认 CPU 正常执行
- ✅ 完整 TCP/HTTP 固件运行（LED=0F = `program_main` 初始化值），确认指令 BRAM 加载正确
- ❌ 以太网 RX 路径待调通：`cpu_rd_empty` 始终为 1，数据包无法到达 CPU FIFO
  - Preamble 已正确添加，eth_presemble 理论上应能检测到
  - 疑似 async FIFO（dual_clock_fifo）在同频读写时钟下的行为差异
  - 疑似 gmii2mac 内部状态机需要特定时序

## TCP FIN 修复 & LED 调试代码清理

### 问题
1. **HTTP 响应后连接不关闭**：`send_http_response()` 发完数据后没有发送 FIN，浏览器/curl 接收完数据后一直等待连接关闭，超时后报错
2. **LED 控制无效**：网页点击按钮后 LED 只闪一下就变回 LED0 常亮，亮度微弱

### 根因分析

**问题1 — 缺少 TCP FIN**
`send_http_response()` 发送 HTTP 数据段（ACK 标志）后直接返回，没有发起 TCP 连接关闭握手。HTTP 响应头写明 `Connection: close` 但 FPGA 侧没有实际关闭连接。

初步尝试在 HTTP 响应后单独发送一个 FIN+ACK 段，但背靠背两次 `send_tcp_seg()` → `LCPU_WR_PUSH_PACKET()` 发包，第二个包（FIN）可能被硬件丢弃或时序冲突。

**问题2 — 调试 LED 覆盖**
`main.c` 主循环末尾有调试代码：
```c
if (iptype == ICMP_PROC) LCPU_SET_LED(0x02);
if (iptype == TCP_PROC)  LCPU_SET_LED(0x01);
```
每次处理 TCP 包后，LED 被强制设为 `0x01`（LED0 常亮）。HTTP 请求设置的 LED 值（如 0x0F）在几微秒内被覆盖，表现为"闪烁一下就灭"，LED0 始终微亮。

### 修复

**修复1 — Piggyback FIN**
将 FIN 标志直接挂在最后一个 HTTP 数据段上一起发送，避免背靠背发包问题：
- `send_http_response()` 新增 `close_after` 参数
- 最后一个 segment 设 `TCP_FLAG_FIN | TCP_FLAG_ACK`
- FIN 消耗一个序列号：`connection_seq_nums[ci]++`
- 发完后状态直接切到 `TCP_STATE_FIN_WAIT_1`

```c
// send_http_response(ci, 1) — piggyback FIN on last data segment
uint8_t flags = TCP_FLAG_ACK;
if (close_after && (offset + chunk >= total))
    flags |= TCP_FLAG_FIN;
...
if (flags & TCP_FLAG_FIN) connection_seq_nums[ci]++;  // FIN seq
```

修复后 curl 正常打印 `shutting down connection #0`，不再超时。

**修复2 — 删除调试 LED**
删除 `main.c` 主循环中的 `LCPU_SET_LED()` 调试代码。LED 值只由 HTTP 请求（`GET /led/XX`）设置，保持到下次网页操作。

### 验证
```bash
ping 169.254.1.1       # 0% loss, 0.8ms
curl http://169.254.1.1/        # 200 OK, 连接正常关闭, 926 bytes HTML
curl http://169.254.1.1/led/0F  # LED 全亮, 保持常亮不闪烁
curl http://169.254.1.1/led/00  # LED 全灭
```
